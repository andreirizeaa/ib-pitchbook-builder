\section{Project Implementation and Outcomes}
\label{sec:implementation}

This section covers what was actually built and why it sometimes diverged from the plan.

\subsection{Architecture Evolution}

The original design called for a Python backend with FastAPI and a Next.js frontend. Two weeks into implementation, this changed. Every data structure that crossed the API boundary had to be defined twice, and when a field name changed in the template schema, the Python definition would update but the TypeScript interface would not, causing silent runtime failures.

Switching everything to TypeScript solved this (SE3). PptxGenJS replaced python-pptx, JSZip with xml2js replaced python-pptx's template reading, and Express.js replaced FastAPI. The migration took four days but removed a whole category of bugs. The \texttt{shared-types} package now defines every interface once, and the TypeScript compiler catches mismatches at build time across all applications.

\subsection{Orchestration Layer}

The orchestration service receives a generation request, runs each stage in sequence, and passes the output of one stage as input to the next: validate input, extract template, retrieve data, plan content, build slides, generate previews, store the result.

The orchestrator stays thin. Each service module handles its own domain, and the orchestrator only manages sequence and error boundaries. If data retrieval fails, it passes an empty data object to the content planner rather than aborting. If the content planner returns invalid JSON after three retries, it logs the failure and returns an error. This separation made it possible to test each service in isolation.

One decision proved especially useful. The orchestrator passes the full template schema to the content planner rather than a summary. Early versions sent only layout names, but the content planner produced better output when it could see placeholder types, sizes, and positions. With the full schema in the prompt, the model had enough context to match content to placeholders correctly, and the unwrapping logic handled the remaining structural quirks.

\subsection{Deck Layouts and Colour Themes}

The system ships with seven deck layouts: Company Overview, Investor Pitch, Market Update, Transaction Summary, Industry Overview, Fundraising Deck, and Due Diligence. Each layout defines a fixed slide sequence with the right number and type of slides for that use case. IB presentations follow predictable formats. A company overview always needs a cover slide, an executive summary, a business description, and financial highlights. The order and structure rarely change between banks. What does change is the visual style: colours, fonts, and logo placement. Each bank has its own brand guidelines.

To handle this, the system separates structure from style. The seven layouts are hardcoded because the slide sequence for a given pitch book type is standard across the industry. The visual style is customisable through eight built-in colour themes (such as Navy \& Gold, Teal \& Coral, and Slate \& Emerald) or by uploading a bank's own template file. When a user uploads a template, the template analyser extracts that bank's exact colours, fonts, and layout positions, and the slide builder applies them to whichever deck layout the user picks. This means a Company Overview generated with one bank's template looks different from one generated with another bank's, even though both follow the same slide structure. \subsection{Core Pipeline}

The generation pipeline follows the design from Section~\ref{sec:research-design}, implemented as a chain of service modules within the Express backend. Each stage is a separate TypeScript module with a defined input/output contract. Development followed a pattern: build the simplest version, test it against real templates, identify the failure mode, and fix it.

\subsubsection{Template Analysis}

The template analyser went through three iterations, each driven by a specific failure in the previous version (SE4).

\textbf{Iteration 1: PptxGenJS only.} The first attempt used PptxGenJS for both reading and writing slides. PptxGenJS can create slides from scratch but has no API for reading existing .pptx files. The only option was to generate new slides and hope the styling matched. It did not. Colours were wrong, placeholder positions were guessed rather than measured, and the output looked nothing like the input template. This approach was scrapped after two days.

\textbf{Iteration 2: JSZip + xml2js (raw XML parsing).} PowerPoint files are ZIP archives containing Office Open XML documents. JSZip opens the archive, and xml2js parses the XML inside. This gave direct access to every property: colours from \texttt{ppt/theme/theme1.xml}, layouts from \texttt{ppt/slideLayouts/}, and placeholder positions from shape definitions. The approach worked but came with a problem. PowerPoint's OOXML specification stores measurements in English Metric Units (EMU), where one inch equals 914,400 EMU. Colours can be stored as hex values, theme references (\texttt{accent1}), or system colour names. Placeholder types use numeric codes, but custom placeholders have no type attribute at all. Each of these required manual parsing and conversion logic.

\textbf{Iteration 3: adding heuristics and fallbacks.} Testing against real corporate templates exposed gaps in the raw XML approach. Custom placeholders with no type attribute made up roughly 30\% of all placeholders in the test set. The analyser added position-based heuristics: a placeholder in the top 15\% of the slide with large font settings is classified as a title, even without a type code. A wide placeholder in the bottom half with small fonts is treated as body text. This brought classification accuracy to 93\% across test templates. When parsing fails entirely (corrupted file, unusual XML structure), the analyser falls back to professional defaults: a navy and gold colour scheme with standard IB layout patterns.

\vspace{0.5em}\filbreak
\begin{lstlisting}[language=JavaScript, caption=Template extraction core logic (simplified)]
async function analyseTemplate(buffer: Buffer): Promise<TemplateSchema> {
  const zip = await JSZip.loadAsync(buffer);

  // Parse theme for colour palette
  const themeXml = await zip.file('ppt/theme/theme1.xml')?.async('string');
  const theme = await parseStringPromise(themeXml);
  const colours = extractColourScheme(theme);

  // Parse each slide layout
  const layouts: SlideLayout[] = [];
  for (const [path, file] of Object.entries(zip.files)) {
    if (path.match(/ppt\/slideLayouts\/slideLayout\d+\.xml/)) {
      const xml = await file.async('string');
      const parsed = await parseStringPromise(xml);
      layouts.push(extractLayout(parsed, colours));
    }
  }

  return { colours, fonts: extractFonts(theme), layouts };
}
\end{lstlisting}

The iterative approach paid off (SE4). Each version failed in a specific, observable way, and the fix was targeted rather than speculative. The unit tests grew alongside the implementation: the first iteration had no tests, the second had basic extraction tests, and the third added tests for edge cases like missing theme files, custom placeholders, and corrupted archives (SE5).

\subsubsection{Content Planning with GPT-4o}

The content planner sends user parameters and the extracted template schema to GPT-4o, requesting a structured content plan. The system prompt (Listing~\ref{lst:system-prompt}) sets the persona, enforces rules about data accuracy, and specifies the exact JSON structure the model must return. Two prompt engineering decisions matter here. First, the prompt bans generic phrasing (`NEVER write generic phrases like ``leading company in its sector''') because early versions produced boilerplate that no banker would use. Second, it specifies minimum content density per slide type, because GPT-4o defaults to sparse output unless told otherwise.

\vspace{0.5em}\filbreak
\begin{lstlisting}[language=JavaScript, caption=Content planner system prompt excerpt (from pitchbook-content.prompt.ts), label=lst:system-prompt]
export const SYSTEM_PROMPT = `You are a senior Managing Director at
Goldman Sachs creating investment banking pitch books.

CRITICAL RULES:
1. ALL financial data MUST use the EXACT numbers provided in the
   user message. NEVER fabricate numbers.
2. Every chart MUST have a "data" array with real numbers.
3. Content must be deeply specific to the company. Mention their
   actual products, markets, competitors, recent events.
4. Write like a real IB analyst: precise, data-driven, no fluff.
5. NEVER write generic phrases like "leading company in its sector"
   or "strong market position". Be SPECIFIC.

CONTENT DENSITY:
- Every Content Slide MUST have at least 5-7 bullet points.
- Every bullet point must be a FULL SENTENCE with specific data.
  BAD: "Strong revenue growth".
  GOOD: "Revenue grew 61% YoY to 130.5B in FY2024, driven by
  Data Center segment expansion to 115.2B."
- Financial Tables should have 4-5 years of data with 5+ rows.

You MUST return JSON in EXACTLY this format:
{ "title": "...", "narrative_arc": "...", "slides": [...] }`;
\end{lstlisting}

Getting valid structured output was the main challenge (SE1). \textcite{lieber2024} found an average JSON success rate of 82.55\% across LLM benchmarks. GPT-4o occasionally returns JSON with extra fields, missing required properties, or wraps the response in an unexpected outer object. One recurring issue during development was GPT-4o nesting the plan inside a wrapper key (e.g., \texttt{\{"pitch\_book": \{...\}\}} instead of the flat structure the schema expects). The content planner handles this with an unwrapping step that detects single-key wrapper objects and extracts the inner value before validation.

The system validates every response using Zod \parencite{zod2024}, a TypeScript-first schema validation library. Zod parses the LLM output at runtime against the expected schema. If the response fails validation, the content planner falls back to a hardcoded plan that uses the correct slide structure and formatting but with generic placeholder content. This means generation never fails entirely, though the fallback output needs more editing. Across the 12 evaluation runs in Appendix~C, all 12 produced valid JSON that passed Zod validation without needing the fallback.

The content planner also receives historical financial data when available. Rather than letting the LLM fabricate numbers, the prompt explicitly provides retrieved data (revenue, market cap, share price) and instructs the model to reference only those figures. The LLM places real numbers rather than making them up, which removes the biggest hallucination risk.

\vspace{0.5em}\filbreak
\begin{lstlisting}[language=JavaScript, caption=Content plan validation with Zod (from pitchbook-content.schema.ts)]
const contentBlockSchema = z.object({
  type: z.enum(['heading', 'paragraph', 'bullet_list',
                'table', 'chart', 'metric']),
  content: z.any(),
});

const slideSchema = z.object({
  index: z.number().optional().default(0),
  title: z.string(),
  layout: z.string().optional().default('Content Slide'),
  talking_points: z.array(z.string()).optional().default([]),
  data_requirements: z.array(z.string()).optional().default([]),
  content_blocks: z.array(contentBlockSchema).optional().default([]),
});

const contentPlanSchema = z.object({
  title: z.string(),
  narrative_arc: z.string().optional().default(''),
  slides: z.array(slideSchema),
});

function parseContentPlan(raw: unknown): ContentPlanOutput {
  return contentPlanSchema.parse(raw);
}
\end{lstlisting}

\subsubsection{Slide Building}

The slide builder takes the content plan and template schema and produces a .pptx file using PptxGenJS (SE10). For each slide in the content plan, it selects the matching layout, creates a new slide, and fills each placeholder with the specified content using the exact formatting from the template schema: font family, size, weight, and colour.

The first version generated slides with correct structure but wrong colours. Some colours were stored as theme references (\texttt{accent1}, \texttt{dk1}) rather than hex values. PptxGenJS has no concept of PowerPoint's theme colour system, so passing theme references through produced default black text on every slide. The fix was a resolver that maps every theme reference to its hex value using the colour palette from the template analyser. A second problem then appeared: some templates use tinted or shaded variants (e.g., \texttt{accent1} at 60\% luminance). The builder now handles these modifiers by applying the percentage to the base hex value.

A separate service, \texttt{template-slide-builder}, handles a different workflow: cloning existing slides from the uploaded template and replacing placeholder text while keeping all visual styling intact. This uses JSZip and the xml2js \texttt{Builder} to modify and regenerate the XML directly, rather than creating slides from scratch via PptxGenJS. Both builders exist because they serve different needs. PptxGenJS creates new slides when the content plan calls for layouts not present in the template. The clone-based builder preserves exact formatting for layouts that already exist.

\subsubsection{Data Retrieval}

The data retrieval service pulls financial information from Yahoo Finance using the \texttt{yahoo-finance2} npm package and SEC EDGAR via its REST API (K5). The orchestrator calls data retrieval before content planning, passing the retrieved data into the LLM prompt so the content planner can reference real figures.

The service caches responses for 24 hours to respect API rate limits during development and evaluation. A fallback mechanism returns graceful null values if an API call fails, allowing generation to proceed with reduced data rather than failing entirely.

\subsubsection{Slide Preview Generation}

Generating PNG previews of .pptx slides is not straightforward in a Node.js environment. The system uses LibreOffice in headless mode to convert the .pptx to PDF, then \texttt{pdftoppm} to render each page as a PNG image. These previews are uploaded to Supabase Storage and their public URLs stored in the database.

This pipeline runs asynchronously after slide generation completes. The web frontend polls for preview availability and displays them as the user browses their pitch books. Neither the preview pipeline nor the add-in described in the next subsection were part of the original design. Both emerged from usability problems discovered during implementation.

\subsection{PowerPoint Add-in}
\label{sec:addin}

The original design assumed users would generate a PB through the web app, download the .pptx file, and edit it in PowerPoint. At the end of iteration 4 (week 7), a walkthrough of the full workflow exposed the flaw. The test was simple: generate a company overview, download it, open it in PowerPoint, notice that one slide needed a different data point, and try to fix it. The fix required going back to the web app, changing the input, regenerating the entire deck, downloading again, opening the new file, and manually copying the one corrected slide into the original. The round trip took eight minutes for a one-sentence change.

This was the opposite of the productivity gain the system was supposed to deliver. The generation itself took 47 seconds, but the surrounding workflow added enough friction to offset the time saved. The review at the end of that iteration flagged this as the highest-priority problem to solve.

The web app could generate slides, but it could not let users edit them. Supporting full PowerPoint editing in a browser (text formatting, shape manipulation, slide reordering, image insertion) would mean rebuilding most of PowerPoint. That was not realistic within the project timeline.

The solution was to bring the generation system into PowerPoint itself. A taskpane add-in built with Office.js runs alongside the user's active presentation. The add-in communicates with the same Express backend as the web app but uses \texttt{Office.context.document} to interact with the open presentation directly.

\subsection{AI Chat Assistant}
\label{sec:ai-chat}

The pitch book viewer includes an AI chat panel (visible in Figure~\ref{fig:pitchbook-viewer}) that lets users request changes to their slides in plain English. A user can type `change the title on slide 3 to Market Opportunities' or `add a bullet point about revenue growth', and the assistant responds with edit instructions tied to specific slides.

The chat runs on GPT-4o-mini, chosen over GPT-4o because the task needs conversational ability rather than structured output. The system prompt includes the number of slides, each slide's title and layout type, and the last 50 messages in the conversation. The model can then reference specific slides by number and see what content already exists before suggesting changes.

\vspace{0.5em}\filbreak
\begin{lstlisting}[language=JavaScript, caption=AI chat service (from ai-chat.service.ts)]
async chat(params: {
  pitchBookId: string;
  message: string;
  slidesData: any[];
  history: Array<{ role: string; content: string }>;
}): Promise<string> {
  const { message, slidesData, history } = params;

  const systemPrompt = `You are a senior IB presentation editor.
Current pitch book has ${slidesData.length} slides:
${slidesData.map((s, i) =>
  `Slide ${i + 1}: "${s.title}" (${s.layout})`).join('\n')}
When the user asks for changes, provide specific instructions.`;

  const response = await openai.chat.completions.create({
    model: 'gpt-4o-mini',
    temperature: 0.4,
    max_tokens: 4096,
    messages: [
      { role: 'system', content: systemPrompt },
      ...history.map(msg => ({
        role: msg.role as 'user' | 'assistant',
        content: msg.content,
      })),
      { role: 'user', content: message },
    ],
  });

  return response.choices[0]?.message?.content
    || 'I could not generate a response. Please try again.';
}
\end{lstlisting}

The backend stores every message in a \texttt{chat\_messages} table linked to the pitch book via foreign key, preserving conversation history across sessions. Row-level security policies ensure users can only access their own chat messages. The chat is advisory: the assistant provides text or instructions, but the user applies the edits.

\subsection{Authentication and Session Management}

Supabase Auth handles user authentication across both the web app and the add-in. The web app uses standard cookie-based sessions via Next.js middleware. The add-in runs inside an iframe within PowerPoint, which blocks cross-origin cookies by default.

The fix uses Supabase's \texttt{createServerClient} with cookie forwarding. The Express backend acts as the single auth source: both the web app and the add-in authenticate through it, and the backend checks session cookies on every request (SE1). This avoids needing separate login flows while working within the iframe's security rules.

\subsection{Scalability Considerations}

The current architecture handles single-user evaluation loads, but two properties make it easier to scale later. The orchestration service runs each pipeline asynchronously: the API returns a job ID immediately and the client polls a \texttt{generations} table for progress updates, so the HTTP connection is not held open during the 30 to 80 second generation. Generated files and preview images are stored in Supabase Storage (backed by S3-compatible object storage) rather than the local filesystem, so the backend is stateless. The main bottleneck at scale would be the sequential GPT-4o API call. A production deployment would need a request queue (Redis or SQS) in front of the orchestrator, allowing multiple generation requests to run in parallel across worker processes.

\subsection{Additions Beyond Original Design}

Two unplanned components, the PowerPoint add-in and the slide preview pipeline, account for roughly a third of total development effort. Both came from testing the planned workflow and finding friction that offset the productivity gains (SE7). The trade-off was dropping RAG search (FR15). The MoSCoW framework made this explicit: the add-in addressed a `Must have' usability gap, while RAG was a `Could have' stretch goal (SE9).
